# Task 43 — Fix RLS punteggi tra membri della stessa lega + test completo FantaTest

## Obiettivo

Correggere il problema per cui un utente autenticato riesce a vedere i propri punteggi nella pagina della lega, ma vede `0`/nessun dato per gli altri partecipanti.

La causa probabile è nelle policy RLS di Supabase:

* `predictions` attualmente consente SELECT solo quando `user_id = auth.uid()`;
* `prediction_entries` consente SELECT solo per predictions appartenenti all'utente corrente;
* `league_members` consente SELECT solo per la propria membership.

### Comportamento desiderato

Un utente autenticato deve poter leggere:

1. le proprie predictions;
2. le predictions degli altri utenti **solo se appartengono alla stessa lega**;
3. le `prediction_entries` relative alle predictions degli utenti della stessa lega;
4. le membership necessarie per visualizzare i partecipanti della propria lega.

Un utente NON deve poter leggere:

* predictions di utenti appartenenti ad altre leghe;
* prediction_entries relative ad altre leghe.

NON modificare:

* dati delle predictions;
* `prediction_entries.points`;
* `total_points`;
* `qualifying_points`;
* `sprint_points`;
* `race_points`;
* `bonus_points`;
* `malus_points`;
* scoring;
* `session_results`;
* schema delle tabelle;
* autenticazione;
* service_role;
* altre RLS non necessarie.

---

# 1. Prima fase — ispezione obbligatoria

Prima di modificare qualsiasi cosa, verificare:

* struttura delle tabelle `leagues`, `league_members`, `predictions`, `prediction_entries`;
* tutte le policy RLS esistenti sulle quattro tabelle;
* presenza di eventuali policy duplicate;
* eventuali query frontend che filtrano erroneamente con `.eq('user_id', currentUserId)`.

Eseguire:

```sql
SELECT
  schemaname,
  tablename,
  policyname,
  permissive,
  roles,
  cmd,
  qual,
  with_check
FROM pg_policies
WHERE schemaname = 'public'
  AND tablename IN (
    'leagues',
    'league_members',
    'predictions',
    'prediction_entries'
  )
ORDER BY tablename, cmd, policyname;
```

Non procedere alla modifica se la struttura reale delle colonne non corrisponde a quella prevista.

---

# 2. Policy SELECT per league_members

Il problema è che attualmente `league_members` permette di vedere solo la propria membership.

Dobbiamo permettere a un membro di vedere tutti i membri delle proprie leghe, ma nessun membro di leghe estranee.

Rimuovere SOLO le vecchie policy SELECT equivalenti alla lettura della propria membership e creare una policy dedicata.

SQL:

```sql
DROP POLICY IF EXISTS "Users can view their own memberships"
ON public.league_members;

CREATE POLICY "Members can view members of their leagues"
ON public.league_members
FOR SELECT
TO authenticated
USING (
  EXISTS (
    SELECT 1
    FROM public.league_members viewer_membership
    WHERE viewer_membership.league_id = league_members.league_id
      AND viewer_membership.user_id = auth.uid()
  )
);
```

IMPORTANTE:

Non modificare le policy INSERT/DELETE esistenti.

---

# 3. Policy SELECT per predictions

Attualmente sono presenti policy equivalenti a:

```text
Users can view own predictions
predictions_select_own
```

Entrambe devono essere rimosse perché limitano la SELECT a:

```sql
user_id = auth.uid()
```

Rimuovere SOLO queste policy:

```sql
DROP POLICY IF EXISTS "Users can view own predictions"
ON public.predictions;

DROP POLICY IF EXISTS "predictions_select_own"
ON public.predictions;
```

Creare quindi una singola policy:

```sql
CREATE POLICY "Members can view predictions in their leagues"
ON public.predictions
FOR SELECT
TO authenticated
USING (
  EXISTS (
    SELECT 1
    FROM public.league_members viewer_membership
    WHERE viewer_membership.league_id = predictions.league_id
      AND viewer_membership.user_id = auth.uid()
  )
);
```

Questa policy significa:

> l'utente può leggere una prediction se appartiene alla stessa `league_id`.

NON usare:

```sql
USING (true)
```

e NON usare:

```sql
USING (user_id = auth.uid())
```

per la nuova policy.

---

# 4. Policy SELECT per prediction_entries

Attualmente sono presenti policy duplicate/equivalenti:

```text
Users can view own prediction entries
prediction_entries_select_own
```

Rimuoverle:

```sql
DROP POLICY IF EXISTS "Users can view own prediction entries"
ON public.prediction_entries;

DROP POLICY IF EXISTS "prediction_entries_select_own"
ON public.prediction_entries;
```

Creare:

```sql
CREATE POLICY "Members can view prediction entries in their leagues"
ON public.prediction_entries
FOR SELECT
TO authenticated
USING (
  EXISTS (
    SELECT 1
    FROM public.predictions p
    JOIN public.league_members lm
      ON lm.league_id = p.league_id
    WHERE p.id = prediction_entries.prediction_id
      AND lm.user_id = auth.uid()
  )
);
```

Questa policy permette di leggere una `prediction_entry` solo quando la prediction appartiene a una lega di cui l'utente corrente è membro.

# 5. NON modificare le policy di scrittura

Le seguenti operazioni devono rimanere limitate al proprietario:

### predictions

INSERT:

```sql

```

UPDATE:

```sql
user_id = auth.uid()
```

DELETE:

```sql

```

### prediction_entries

INSERT/UPDATE/DELETE devono continuare a verificare che la prediction appartenga all'utente corrente.

NON trasformare queste policy in policy basate sulla membership della lega.

Un membro della lega deve poter leggere i punteggi degli altri, ma NON modificare i loro pronostici.

# 10. Test FantaTest — prediction_entries

Con USER_A autenticato:

```sql
SELECT
  pe.id,
  pe.prediction_id,
  pe.prediction_type,
  pe.position,
  pe.rider_id,
  pe.points
FROM public.prediction_entries pe
JOIN public.predictions p
```

Devono essere visibili le entries di tutti i partecipanti di FantaTest.
