# Task #17 — Configurare accesso SQL read-only a Supabase e analizzare `score_prediction`

## Obiettivo

Configurare, se possibile, un canale **SQL read-only** verso il database PostgreSQL di Supabase attualmente utilizzato dall'applicazione.

L'obiettivo è esclusivamente analizzare il database e recuperare la definizione reale della RPC:

```sql
public.score_prediction(p_prediction_id uuid)
```

**Non modificare dati, RPC, schema, RLS, migration o codice applicativo.**

---

## 1. Verifica della connessione

Verificare se nell'ambiente Replit è disponibile una connessione PostgreSQL che punti realmente al database Supabase.

Non utilizzare:

```text
DATABASE_URL
```

se punta a `heliumdb`/PostgreSQL Replit interno.

Individuare invece eventuali variabili o connection string specificamente associate a Supabase.

**Non stampare, salvare o riportare credenziali, password, token o connection string complete nei log o nei file.**

È sufficiente verificare:

* host/database di destinazione;
* raggiungibilità;
* autenticazione;
* permessi read-only.

---

## 2. Accesso esclusivamente read-only

Se è disponibile una connessione Supabase PostgreSQL autorizzata, utilizzarla esclusivamente per query `SELECT`.

Sono consentite query di introspezione PostgreSQL come:

```sql
SELECT current_database();
SELECT current_user;
SELECT version();
```

e query sui cataloghi PostgreSQL/information schema.

NON eseguire:

```text
CREATE
ALTER
DROP
INSERT
UPDATE
DELETE
TRUNCATE
GRANT
REVOKE
```

Non creare fixture.

Non chiamare `score_prediction`.

Non modificare prediction esistenti.

---

## 3. Recuperare la definizione reale della RPC

Utilizzare i cataloghi PostgreSQL per verificare:

* schema;
* nome funzione;
* argomenti;
* return type;
* linguaggio;
* corpo SQL/PLpgSQL, se disponibile.

In particolare cercare la definizione di:

```text
public.score_prediction(uuid)
```

e recuperare, se i permessi lo consentono, il risultato equivalente a:

```sql
pg_get_functiondef(...)
```

Verificare anche:

```text
proargnames
proargtypes
prorettype
prokind
provolatile
prosecdef
```

Non modificare la funzione.

---

## 4. Analizzare lo scoring effettivamente implementato

Una volta recuperato il corpo SQL, analizzarlo senza modificarlo.

Documentare separatamente:

### Qualifica

* Pole;
* tempo Pole;
* soglie;
* gestione errori/null;
* funzione `calculate_qualifying_time_points`.

### Sprint

* punti posizione;
* gestione piloti non classificati;
* gestione piloti assenti;
* eventuali bonus/malus.

### Gara

* punti P1-P5;
* comportamento P5 → P6;
* pilota oltre P5;
* piloti non classificati;
* bonus ordine;
* bonus Top 5;
* bonus 4 piloti;
* bonus 3 piloti;
* cumulabilità dei bonus.

### OUT

Determinare esattamente:

* da dove viene letto il pilota OUT;
* come viene confrontato con i risultati ufficiali;
* quali status generano il bonus;
* valore del bonus;
* cosa accade se OUT è anche nella Top 5;
* cosa accade se OUT è assente dal risultato.

### Malus

Determinare esattamente:

* quali status generano malus;
* come vengono conteggiati;
* eventuali soglie;
* eventuale limite massimo;
* se il pilota OUT entra o meno nel conteggio.

### Totale

Documentare la formula finale e l'ordine con cui vengono applicati:

```text
Qualifica
+ Sprint
+ Gara
+ Bonus
+ Bonus OUT
- Malus
= Totale
```

Se l'implementazione differisce, riportare la formula effettiva.
