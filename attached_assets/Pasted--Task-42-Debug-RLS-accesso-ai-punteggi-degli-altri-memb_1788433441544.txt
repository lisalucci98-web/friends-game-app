# Task 42 — Debug RLS / accesso ai punteggi degli altri membri della lega

## PROBLEMA OSSERVATO

È stato effettuato un test reale accedendo alla stessa lega con due account differenti.

Risultato:

### Account Nicholas

* Nicholas vede correttamente i propri punteggi;
* tutti gli altri partecipanti risultano con punteggio 0 / senza dati.

### Altro account

* il secondo utente vede correttamente i propri punteggi;
* Nicholas e gli altri partecipanti risultano con punteggio 0 / senza dati.

Questo indica fortemente che i dati visualizzati dalla pagina sono limitati dall'utente autenticato.

## IPOTESI PRINCIPALE

Verificare se il problema è causato da:

1. RLS sulle tabelle `predictions` o `prediction_entries`;
2. query che applica `auth.uid()` / `currentUserId`;
3. RPC che restituisce soltanto i dati dell'utente corrente;
4. relazione tra `league_members`, `predictions` e `prediction_entries`;
5. combinazione di RLS + query frontend.

NON assumere che il problema sia frontend.

---

# 1. OBIETTIVO

La pagina:

```text
/leghe/:leagueId
```

deve permettere a un membro della lega di vedere i punteggi degli **ALTRI membri della stessa lega**.

Regola desiderata:

```text
utente autenticato
       ↓
verifica che appartenga alla lega
       ↓
può leggere i punteggi di TUTTI i membri di quella lega
```

NON:

```text
utente autenticato
       ↓
può leggere soltanto predictions.user_id = auth.uid()
```

---

# 2. MODELLO DI AUTORIZZAZIONE DESIDERATO

L'accesso deve essere basato sull'appartenenza alla lega.

Se:

```text
user A ∈ league X
```

allora A può leggere i dati necessari per visualizzare i punteggi di:

```text
user A
user B
user C
...
```

purché:

```text
user B ∈ league X
user C ∈ league X
...
```

NON deve poter leggere i dati di utenti appartenenti a leghe completamente diverse.

Quindi la condizione concettuale è:

```text
prediction.user_id appartiene a league_members
WHERE league_members.league_id = currentLeagueId
```

e non:

```text
prediction.user_id = auth.uid()
```

---

Prima di modificare qualsiasi cosa, analizza:

### `league_members`


# 4. VERIFICA RLS

Controlla le policy RLS attualmente presenti su:

```text
predictions
prediction_entries
league_members
```

NON modificarle ancora.

Identifica esplicitamente:

```text
SELECT policy
INSERT policy
UPDATE policy
DELETE policy
```

e soprattutto la condizione `USING` / `WITH CHECK`.

Cerca condizioni come:

```text
auth.uid()
```

```text
user_id = auth.uid()
```

```text
prediction.user_id = auth.uid()
```

o equivalenti.

# 7. SE IL PROBLEMA È RLS

Se la diagnosi dimostra che RLS impedisce a un membro della lega di leggere le prediction degli altri membri della stessa lega:

1. documenta la policy attuale;
2. prepara una nuova policy che consenta la lettura solo quando il record appartiene a una lega di cui `auth.uid()` è membro;
3. verifica che l'accesso rimanga limitato alla lega.

La condizione concettuale deve essere:

```text
EXISTS (
  SELECT 1
  FROM league_members lm_viewer
  JOIN league_members lm_owner
    ON lm_owner.league_id = lm_viewer.league_id
  WHERE lm_viewer.user_id = auth.uid()
    AND lm_owner.user_id = predictions.user_id
    AND lm_viewer.league_id = <league della prediction>
)
```

Adatta la query allo schema reale del progetto.

NON copiare questa SQL alla cieca: prima verifica le FK e i nomi effettivi delle colonne.

---

# 8. ATTENZIONE ALLE PREDICTION_ENTRIES

Se `predictions` diventa leggibile ma `prediction_entries` rimane limitata a:

```text
auth.uid()
```

il problema non sarà completamente risolto.

Verifica quindi entrambe le tabelle.

La catena deve essere leggibile per tutti i membri della lega:

```text
league_members
       ↓
predictions
       ↓
prediction_entries
```

---

# 9. VERIFICA FRONTEND

Solo dopo aver verificato RLS, controlla la query della pagina `/leghe/:leagueId`.

La query deve poter recuperare le prediction di tutti gli utenti della lega.

Cerca eventuali filtri:

```text
.eq('user_id', currentUserId)
```

```text
.eq('user_id', user.id)
```

```text
user_id === currentUserId
```

o equivalenti.

Se esistono, rimuovili SOLO se applicati al caricamento dei dati della lega.

Il controllo:

```text
currentUser appartiene alla lega
```

deve rimanere.

---

# 10. NON CONFONDERE AUTORIZZAZIONE E FILTRO UI

